# Конфигурация сервера

Копии того, что реально стоит на `144.31.221.179`. Живой экземпляр — на самом
сервере; здесь он лежит, чтобы его можно было прочитать, обсудить в диффе и
восстановить, если машина пропадёт. Раньше эти файлы существовали в одном
экземпляре и нигде не были записаны.

**Эта папка не выкладывается на сайт** — она перечислена в `.assetsignore`,
поэтому `tools/deploy.sh` её не отправляет.

| Файл здесь | Где на сервере |
|---|---|
| `nginx-site.conf` | `/etc/nginx/sites-available/ironvane-media` |
| `nginx-headers.conf` | `/etc/nginx/snippets/ironvane-headers.conf` |
| `nginx-csp.conf` | `/etc/nginx/conf.d/ironvane-csp.conf` |
| `telegram.ini.example` | `/etc/ironvane/telegram.ini` — **без значений** |

Токена здесь нет и быть не должно. `telegram.ini.example` показывает только
форму файла; настоящий заполняется на сервере и никогда не коммитится.

## Это копии, а не источник

Никакой автоматической связи между этой папкой и сервером нет. Правка здесь на
сервер не поедет, и наоборот. Если меняете конфигурацию:

1. правите на сервере, проверяете `nginx -t`, перезагружаете;
2. копируете сюда и коммитите, чтобы копия не разошлась с оригиналом.

Сверить, не разошлись ли они:

```bash
ssh -i ~/.ssh/ironvane_ed25519 root@144.31.221.179 \
  'cat /etc/nginx/sites-available/ironvane-media' | diff - server/nginx-site.conf
```

## Осторожно с certbot

`certbot` правит `nginx-site.conf` сам. При выпуске сертификата 25.08.2026 он
заменил блок для порта 80 своим — и сгенерированный блок не содержал ни
заголовков безопасности, ни `server_tokens off`, а перенаправление слал кодом
301 вместо 308, из-за чего POST по `http://` превращался в GET. Это
восстановлено вручную; если certbot когда-нибудь снова перепишет этот блок,
сверьтесь с копией отсюда.

Причины, по которым конфиг устроен именно так, расписаны в комментариях внутри
файлов и в [../docs/server.md](../docs/server.md).

## systemd-restart.conf

Кладётся на сервере в два места:

- `/etc/systemd/system/nginx.service.d/restart.conf`
- `/etc/systemd/system/php8.3-fpm.service.d/restart.conf`

После правки — `systemctl daemon-reload`. Ubuntu поставляет обе службы без
политики перезапуска, то есть упавший процесс остаётся лежать; этот файл
поднимает его через пять секунд.

## sshd-99-ironvane.conf и fail2ban-sshd.local

Кладутся в `/etc/ssh/sshd_config.d/99-ironvane.conf` и
`/etc/fail2ban/jail.d/sshd.local`.

**Осторожно с порядком.** В настройках SSH побеждает первое встреченное
значение, а не последнее, и `50-cloud-init.conf` из образа Ubuntu читается
раньше. Всё, что там задано, наш файл переопределить не сможет. Проверять
результат, а не файл:

```bash
sshd -T | grep -E "passwordauthentication|permitrootlogin"
```

fail2ban при первом запуске нашёл в журнале 78 неудачных попыток входа и сразу
заблокировал шесть адресов. Это фон, а не происшествие: публичный IP с открытым
портом 22 перебирают непрерывно.

## ironvane-sync и его таймер

`ironvane-sync` кладётся в `/usr/local/bin/`, два файла с расширениями
`.service` и `.timer` — в `/etc/systemd/system/`. После правки:

```bash
systemctl daemon-reload
systemctl restart ironvane-sync.timer
```

Это тот самый механизм, из-за которого сайт больше не зависит от чьего-либо
компьютера: сервер сам смотрит в GitHub каждые пять минут. Подробности и схема
— в [../docs/server.md](../docs/server.md).

Обратите внимание: скрипт читает исключения из `.assetsignore` в самом
репозитории, а не из своей копии. Список того, что нельзя публиковать, живёт в
одном месте и одинаков для автоматической выкладки и для `tools/deploy.sh`.

## nginx-ratelimit.conf

Кладётся в `/etc/nginx/conf.d/ironvane-ratelimit.conf`. Задаёт три зоны учёта:
общая для сайта (20 запросов в секунду на адрес), отдельная и жёсткая для
приёма заявок (6 в минуту) и ограничение одновременных соединений. Сами
директивы `limit_req` стоят в блоках `location` файла `nginx-site.conf`.

Считается по **настоящему** адресу: nginx держит его в памяти
(`$binary_remote_addr`), и маскировка в логах на это не влияет. То есть
ограничение точное, а на диск адрес по-прежнему не попадает.

Ответ — **429**, а не 503: «слишком часто» относится к клиенту, а не к сбою
сервера, и поисковик, получив 503, начинает считать сайт неисправным.

Проверено под настоящим потоком: из 120 одновременных запросов к странице
прошло 48, отбито 72; из 30 к `/api/lead` прошло 4, отбито 26. Обычный доступ
восстанавливается сразу — это ограничение, а не бан.

**Чего это не делает.** Объёмную атаку сервер не переживёт в любом случае:
канал забивается до того, как nginx увидит первый запрос. Для этого нужен
посредник выше — Cloudflare с включённым проксированием. Здешние пороги
отбивают то, что реально приходит каждый день: сканеры уязвимостей и спам в
формы.
