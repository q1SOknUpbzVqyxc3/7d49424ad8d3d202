### Две вещи, на которых уже обожглись

**Настройки SSH: побеждает ПЕРВОЕ значение, а не последнее.** Основной файл
`/etc/ssh/sshd_config` подключает каталог `sshd_config.d/*.conf` в самом начале,
и файлы читаются по алфавиту. Образ Ubuntu кладёт туда `50-cloud-init.conf` с
`PasswordAuthentication yes`, поэтому наш `99-ironvane.conf` с `no` два дня
молча игнорировался. Вход root по паролю всё это время был закрыт другой
директивой — `PermitRootLogin prohibit-password`, её cloud-init не трогает, — но
сама настройка не действовала, и появись на сервере второй пользователь, он
заходил бы по паролю. **Проверять надо не файл, а результат:**

```bash
sshd -T | grep -E "passwordauthentication|permitrootlogin"
```

**Пароль в файле может разойтись с паролем на сервере.** Именно так и вышло:
записанный в `ironvane-server.txt` пароль сервер не принимал. Приведены в
соответствие 02.09.2026 и проверены живым входом. Меняя пароль, проверяйте
вход, а не только успешность команды.

## Обновить сайт

**Отправить правку в GitHub — и всё.** Сервер сам заберёт её в течение пяти
минут:

```
правка  →  git push  →  GitHub  →  сервер забирает раз в 5 минут  →  сайт
```

Ничей компьютер в цепочке не участвует. Так сделано 02.09.2026 по просьбе
владельца: он не хочет, чтобы сайт зависел от его машины.

### Как это устроено

| | |
|---|---|
| Копия репозитория | `/opt/ironvane-media` |
| Скрипт | `/usr/local/bin/ironvane-sync` |
| Расписание | `ironvane-sync.timer`, каждые 5 минут |
| Журнал | `/var/log/ironvane-sync.log` |
| Ключ для чтения GitHub | `/root/.ssh/github_deploy` |

Скрипт смотрит, не появился ли в GitHub новый коммит. Если нет — выходит
молча. Если есть — забирает, собирает каталог рядом с боевым, исключая всё
внутреннее по списку из `.assetsignore`, и **подменяет одним движением**, чтобы
обрыв на середине не оставил посетителю полусайта. После этого сам проверяет,
что все пять языков отвечают, и пишет результат в журнал.

Посмотреть, что происходило:

```bash
tail -20 /var/log/ironvane-sync.log
```

Запустить немедленно, не дожидаясь таймера:

```bash
systemctl start ironvane-sync
```

### Ключ доступа к GitHub

Закрытая половина создана на сервере и оттуда никогда не уходила. В GitHub, в
разделе Deploy keys репозитория, лежит только открытая — **без права записи**.
Это намеренно: сервер должен уметь читать репозиторий и не должен уметь его
портить. Если сервер когда-нибудь скомпрометируют, история в GitHub уцелеет.

### Запасной путь: выкладка вручную

```bash
bash tools/deploy.sh
```

Работает по-прежнему и делает то же самое, но **с той машины, где запущен**, и
в обход GitHub. Нужен, если GitHub недоступен или надо срочно выложить что-то,
чего в репозитории ещё нет. Пользуясь им, помните: следующая же автоматическая
синхронизация вернёт сайт к тому, что лежит в GitHub. Ручная выкладка — это
временная мера, а не способ работы.

Ни один из двух путей не трогает настройки nginx, PHP и сертификат — только
файлы сайта.

## Что стоит на сервере

| | |
|---|---|
| Веб-сервер | nginx 1.24 |
| PHP | 8.3.6 (FPM), модули curl, mbstring, json |
| Сертификаты | certbot 2.9, автопродление включено |
| Firewall | ufw: открыты только 22, 80, 443 |
| Защита от перебора | fail2ban: 5 промахов подряд — блокировка на час |
| Обновления | unattended-upgrades, ставятся сами |

Файлы сайта: `/var/www/ironvane-media`

Конфигурация:

- `/etc/nginx/sites-available/ironvane-media` — сам сайт
- `/etc/nginx/snippets/ironvane-headers.conf` — шесть заголовков безопасности
- `/etc/nginx/conf.d/ironvane-csp.conf` — политика содержимого, только для страниц
- `/etc/ironvane/telegram.ini` — токен бота, вне каталога сайта
- `/var/log/php-ironvane.log` — ошибки приёма заявок
- `/etc/ssh/sshd_config.d/99-ironvane.conf` — вход по SSH
- `/etc/fail2ban/jail.d/sshd.local` — правило блокировки перебора

### Почему заголовки лежат отдельным файлом

В nginx `add_header` в дочернем блоке **отменяет** унаследованные, а не
дополняет их. Каждый блок, который ставит свой заголовок, обязан повторить все
остальные — отсюда отдельный файл и `include` в каждом таком месте. Забыть об
этом означает молча потерять защиту на части ответов.

### Почему годовой кеш без `always`

Правило кеша для `/assets/` намеренно не помечено `always`. С этим словом
заголовок лёг бы и на ответ 404, и опечатка в имени картинки залипла бы у
посетителя в браузере на год без возможности сбросить. Та же логика была в
`worker.js`, по той же причине.

## DNS и сертификат

Домен `ironvane-media.com` куплен 24.08.2026 через Telegram-бота `@VPSPay_bot`,
регистратор за ним — 1REG. Записи правятся в боте: меню домена → **«1REG DNS»**.
Серверы имён домена — Cloudflare (`adele.ns.cloudflare.com`,
`ray.ns.cloudflare.com`), но панель 1REG пишет именно в живую зону, так что
менять их не нужно.

| Имя | Тип | Значение |
|---|---|---|
| (пусто) | A | `144.31.221.179` |
| `www` | A | `144.31.221.179` |

**Грабли в этой панели.** Поле «Имя хоста» — это то, что стоит ПЕРЕД доменом, а
не адрес сервера. Если вписать туда IP, создастся запись
`144.31.221.179.ironvane-media.com`, которая ни на что не влияет, а домен
останется нерабочим. Для самого домена поле оставляют пустым. На эти грабли уже
наступили один раз.

Проксирование Cloudflare намеренно выключено — трафик идёт напрямую на сервер.
Если когда-нибудь его включат, режим SSL обязан быть **Full (strict)**: при
Flexible Cloudflare ходит к серверу по обычному HTTP, сервер перебрасывает на
HTTPS, и получается петля, при которой сайт просто перестаёт открываться.

Сертификат Let's Encrypt выпущен 25.08.2026 на `ironvane-media.com` и
`www.ironvane-media.com`, зарегистрирован **без почты** — уведомлений об
истечении не будет, продление автоматическое. Проверить руками:

```bash
certbot certificates
certbot renew --dry-run
```

## Что работает само, без человека

Никто за этой машиной не следит, поэтому она должна поднимать себя сама.

| | |
|---|---|
| Обновления безопасности | ставятся сами, `unattended-upgrades` |
| Продление сертификата | само, таймер certbot; проверено симуляцией |
| Запуск после перезагрузки | nginx, PHP-FPM, firewall — все `enabled` |
| Падение службы | перезапуск через 5 секунд, `Restart=on-failure` |

Ubuntu ставит nginx и PHP-FPM **без** политики перезапуска: упавший процесс
так и лежит, пока человек не заметит. Добавлено 25.08.2026 в
`/etc/systemd/system/<служба>.service.d/restart.conf`.

Проверено не по конфигу, а делом: nginx убит сигналом KILL, поднялся сам за
девять секунд, сайт снова отвечал 200.

**Чего автоматика не делает.** Никто не проверяет, что сайт открывается — если
сервер отключат за неуплату или его заблокируют, узнаете об этом сами. Как
появится Telegram-бот для заявок, через него же можно повесить проверку раз в
пять минут с сообщением при недоступности.

## Приём заявок

Работает с 02.09.2026. Бот **`@ironvane_arbi_bot`**, уведомления приходят
**в личную переписку** владельца с ботом, а не в группу. Группа была бы лучше —
заявку видит команда, и она не теряется вместе с одним человеком. Переключается
сменой `TELEGRAM_CHAT_ID`.

**Бота уже один раз удалили по ошибке** (10.09.2026, прежний назывался
`@arbitrage_ironvane_bot`). Сайт этого не заметил: заявки продолжали
записываться в архив, и после подстановки нового токена две накопившиеся были
разосланы из него же. `TELEGRAM_CHAT_ID` при этом менять не пришлось — для
личной переписки это идентификатор человека, а не бота, и новый бот пишет по
нему же, как только человек ему написал.

Токен и ID чата лежат в `/etc/ironvane/telegram.ini`, права `root:www-data 640`,
вне каталога сайта. После правки файла нужен `systemctl restart php8.3-fpm`.

### Заявка сначала записывается, потом отправляется

Каждое обращение уходит строкой JSON в `/var/lib/ironvane/leads.jsonl` **до**
вызова Telegram. Читать так:

```bash
tail -5 /var/lib/ironvane/leads.jsonl | php -r 'while($l=fgets(STDIN)){$j=json_decode($l,true);echo $j["at"]." ".$j["fields"]["email"]."\n";}'
```

**Зачем это появилось.** С 26.08 по 02.09 на `/api/lead` пришли четыре
обращения, пока токена ещё не было. Все четыре получили 500 и пропали
бесследно: тело запроса нигде не пишется, а обработчик падал до отправки. Все
четыре при этом прошли ловушку для ботов и проверку почты — то есть это были
либо живые люди, либо неплохие боты, и выяснить это уже нельзя. Отправка и
запись были одним действием; теперь они разделены, и сбой Telegram стоит
уведомления, а не клиента.

Архив — подстраховка, а не условие: если файл не пишется, это уходит в лог, а
отправка идёт своим чередом. Посетитель не должен терять сообщение из-за
переполненного диска.

Файл хранит персональные данные, поэтому лежит вне раздачи, читается только
веб-сервером и ротируется помесячно с хранением 24 месяцев — тот же срок, что
политика конфиденциальности обещает для обращений.

### Адреса маскируются в двух местах, а не в одном

nginx пишет `109.229.28.0` вместо полного адреса (`conf.d/ironvane-anonlog.conf`).
Но PHP видит в `REMOTE_ADDR` настоящий, и первая версия архива честно его
записывала — то есть возвращала обратно ровно то, что маскировка убирала.
Поэтому в `api/lead.php` есть своя `maskIp()`. **Правя одно, проверяйте
второе.**

Журнал SSH намеренно НЕ маскируется: fail2ban нужен настоящий адрес атакующего.

## Что осталось от Cloudflare

`worker.js` и `wrangler.jsonc` пока лежат в репозитории и в выкладку не
попадают. Старый адрес на `workers.dev` всё ещё жив и остаётся запасным
вариантом. Удалять их стоит после того, как новый сервер отработает без
нареканий пару недель.

Логика приёма заявок из `worker.js` перенесена в `api/lead.php` один в один;
не перенеслась одна мелочь — Cloudflare добавлял к заявке страну посетителя,
обычный сервер этого не умеет, поэтому строка «Гео» из уведомлений исчезла.
